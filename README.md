# DiaboliX

DiaboliX is a local autonomous coding harness for OpenAI-compatible models. A single Frontier agent investigates, plans, edits and verifies work using integrated tools; an independent model review is available when the agent explicitly requests it.

> [!CAUTION]
> **Trading is not even alpha software.** It is an unfinished reminder of a possible future idea, not a usable feature. Do not use the Trading profile, exchange integrations, or trading tools for real trading, paper trading, investment decisions, or financial analysis. They are not validated, may behave unpredictably, and must not be trusted with money or accounts. Use the Coding profile.

## Getting started

You need Node.js 20 or later, Docker Engine or Docker Desktop, and permission to use Docker. From the project directory, run:

```sh
npm install
docker build -t diabolix-sandbox:local sandbox
npm start
```

Open [http://localhost:6660](http://localhost:6660). Enter an OpenAI-compatible endpoint, an API key if required, a model, and an absolute path to the project. Model discovery uses `/models`; the agent uses `/chat/completions` with tool calling. For a local API, enter an address reachable from the computer running Node.js.

The connection settings let you choose a model and general reasoning effort, with an optional model and effort override for explicitly requested reviews. The default omits the `reasoning_effort` parameter; other choices send it with each applicable chat request. Available and effective levels depend on the model and provider, which may reject or ignore unsupported values. Longer reasoning requests have a five-minute per-attempt timeout and remain cancellable with Stop.

Settings are saved in `config.local.json`. By default, the API key remains in process memory; you can explicitly choose to save it locally. The current model conversation remains in process memory; task events are stored separately as described below.

## Working profiles

The profile selector in the header switches between **Coding** (the default) and **Trading** and saves the choice in `config.local.json`. Both use the configured MCP server, and both retain its web tools. Coding excludes MCP tools named `exchange_*`, the former `paper_exchange_*` names, and common trading aliases; it omits the built-in trading prompts. Trading exposes the complete MCP tool list and trading instructions. Model settings are shared by the two profiles, while chat context, read cache, and session telemetry are kept separately. In Telegram, `/set profile coding` and `/set profile trading` change the same setting.

If MCP is unavailable, Coding emits a warning and continues with built-in tools; Trading reports the connection failure. Filtering is based on tool names, not a security boundary: an external server can expose trading capabilities under other names, and enabled Computer Use has its own permissions. Connect only trusted servers.

## Isolation

The web server and provider requests run on the host. Most built-in tools run in short-lived Docker containers without the Docker socket, as an unprivileged user with a read-only root filesystem and limits on CPU, memory, and process count. Ordinary commands have no network access. `process_start` can instead lazily create a task-scoped offline Docker container for a local server, debugger or piped REPL; `process_read` and `process_write` use its per-task process IDs. These are not full interactive PTYs, and processes do not persist across tasks or server restarts. The dedicated dependency installer uses a temporary isolated Docker network and a separate proxy restricted to the official npm and PyPI hosts.

The selected project is mounted read-write at `/workspace`: changes affect the actual files on the host. Do not select your entire home directory or keep secrets in the selected folder. The agent can use `install_dependencies` to install npm packages into the project or Python packages into a project-local `.venv`; these persist across commands and the root project's virtual environment is added to the command PATH. The Python environment is intended for the Linux sandbox, not for use directly on the host. Installation can change package manifests and lock files. The installer defaults to disabling npm lifecycle scripts and allowing only binary Python wheels; the agent can enable scripts or Python source builds when required. Such code can modify the mounted project. Packages that download binaries from other hosts may fail because the proxy only permits `registry.npmjs.org`, `pypi.org` and `files.pythonhosted.org`. A container is not a substitute for a full virtual machine; its security depends on Docker and the host. On Linux, the selected folder may need to be writable by UID 1000. If Docker or the sandbox image is unavailable, tools return an error and do not run on the host.

The system prompt describes this isolation to the model. The task-scoped container is closed when a task ends or is stopped; if Docker cannot confirm removal, the task reports an error and rollback is blocked pending manual review. Unexpected host or daemon failures can leave cleanup uncertain. The container can execute user-supplied commands and its writable workspace is real host data; process output can contain secrets. The provider receives the task and tool results, so choose a provider you trust.

## Built-in web MCP server

DiaboliX starts its own MCP endpoint at `http://127.0.0.1:6660/mcp` alongside the web UI and uses it by default. The endpoint exposes `web_search` and `read_web_page`. When Computer Use is enabled, it also exposes the task-scoped `computer` tool. Its random per-process bearer token is held by the local DiaboliX process; the endpoint is not intended for direct browser access. The MCP server runs on the host, outside the agent's network-isolated Docker sandbox.

Choose **Automatic**, **Tavily**, or **Brave Search** in the connection settings. In Automatic mode, DiaboliX uses Tavily when its key is configured, then Brave when its key is configured, then the unofficial DuckDuckGo HTML endpoint, with a limited Wikipedia fallback. A selected provider reports errors instead of silently switching services. The result identifies its provider; public HTML endpoints may change or be unavailable.

Enter the Tavily or Brave Search API key in the UI, or set `TAVILY_API_KEY` or `BRAVE_SEARCH_API_KEY` before starting DiaboliX. A UI key takes precedence over the corresponding environment variable. Keys remain in memory by default; each can optionally be saved in `config.local.json` without encryption. Keys are not returned to the browser. You can remove a UI key in settings; an environment key remains active if set. For example, to configure Tavily without the UI:

```sh
export TAVILY_API_KEY='your-key'
npm start
```

The page reader accepts public HTTP(S) pages on standard ports and returns limited plain text. It does not execute JavaScript. Requests to loopback, private, link-local and other non-public addresses are blocked, including DNS answers and redirects. Responses, redirects, request duration and concurrency are limited. Web content and MCP tool outputs are untrusted data; queries and retrieved content may be sent to the search provider and the configured model provider. The two web tools are read-only; the optional Computer Use tool can modify the workspace.

You may replace the MCP URL in settings with another trusted Streamable HTTP server, or clear it to disable MCP. External MCP servers execute tools outside the Docker sandbox, with their own permissions. External MCP authentication and stdio connections are not currently supported.

The optional **MCP: only tools declared read-only** setting hides tools whose server does not advertise `readOnlyHint: true`. The event log summarizes server-declared annotations. These are claims made by the MCP server, not enforced permissions: a malicious or incorrect server can mislabel a tool, and this filter does not sandbox it. The filter is off by default for backward compatibility; it can hide Computer Use and other tools.

## Telegram bot

Create your own bot with [BotFather](https://t.me/BotFather), obtain your numeric Telegram user ID from a trusted client or bot, and enter both in **Connection → Telegram Bot**. Enable Telegram control, save the settings, then open your bot in Telegram and send `/start`. The connection status appears in the settings. DiaboliX must remain running on your computer and be able to reach the Telegram Bot API.

Only messages in a private chat where both the sender ID and chat ID match the configured numeric ID are accepted. Group messages, forwarded messages, and messages sent before the current connection started are ignored. The bot uses long polling, so no incoming public port is needed. Long polling requires a dedicated bot without an active webhook; DiaboliX reports an existing webhook and does not delete it. Do not run another poller with the same bot token.

Send a task as ordinary text or `/task <task>`. The bot sends agent messages and completion or error notifications, including for tasks started from the web UI. Commands: `/status`, `/logs` (download the event log), `/stop`, `/new`, `/changes` (download the task diff), `/screen` (latest Computer Use screenshot), `/rollback` (roll back the completed task), `/models`, `/settings`, `/set <name> <value>`, and `/help`. The help message lists configurable names. Only one task can run at a time, and settings cannot be changed while it is running. Telegram linking and its allowed ID are managed in the local UI. Attachments are limited to 40 MB and `/changes` uses the shadow-checkpoint exclusions described below.

The bot token is saved in `config.local.json` **without encryption by default**, with owner-only file permissions. You can disable this in settings; the token then remains only in memory and must be entered again after a restart. Removing the token disconnects the bot. The API returns only a presence flag, not the token. Tasks, messages, diffs and screenshots sent via the bot pass through Telegram; commands containing API keys remain in the Telegram chat history. Prefer entering credentials in the local UI. The configured local settings file is masked inside the built-in sandbox and Computer Use containers when it lies in the mounted workspace. This does not protect copies of the file or external MCP servers running on the host.

## Limitations

This is an early harness implementation. It does not provide persistent model conversation history, command approval, or a full sandbox for third-party MCP servers.

## Agent workflow

One Frontier agent works directly on the user task. It receives a compact project map and task-relevant context, chooses and invokes tools, and decides when to inspect, modify or validate the project. The harness retains loop guards, bounded context, post-edit diagnostics and evidence freshness checks. The agent can call `request_review` for an independent reviewer when useful; this is not an automatic stage. That reviewer receives a bounded, journal-linked current file inventory and a diff from the same Shadow Git tree, and may inspect files, search code and check exact paths. The inventory excludes protected, binary, dependency and symlink paths, so an omitted entry does not prove absence. Historical research is not evidence of the current workspace. A tree change during review invalidates its verdict; the agent remains responsible for subsequent action.

`read_file` supports windows of up to 250 lines; `search_code` returns up to 50 matches; `patch_file` edits a single exact match and supports rollback. `write_file` creates files and permits explicit `overwrite: true`. Identical patch replacements are rejected; missing and ambiguous targets produce distinct suggestions. Reconnaissance excludes dependency and build directories, lock files, and binary files. The map contains only paths and symbol names, is limited to 6 KB, and covers up to 300 ranked text files from up to 30,000 discovered paths; ranking by task terms is heuristic and can omit relevant files. The reviewer's diff is generated separately from Shadow Git across included text files and is output-limited. If it is truncated, the reviewer should inspect files with its tools.

Additional built-in tools complement the existing tools:

- `project_state` lists included text files and their changes relative to the task baseline, can check an exact path and hash, and reports available test and diagnostic results with freshness information. It does not inventory excluded paths or binary files.
- `code_navigation` uses ast-grep for symbol, import and structural searches, and language servers for definitions, references and file diagnostics in JavaScript, TypeScript and Python. LSP results depend on the project configuration and dependencies; the diagnostic response may be incomplete when analysis takes longer than the wait. `module_map` provides a paginated syntactic import map. It does not resolve runtime imports or aliases; use LSP for semantic navigation. Language servers are started per request rather than kept resident.
- `smart_edit` replaces a unique symbol or a line range in an existing file. It requires a current SHA-256, checks syntax where supported, returns the actual diff and supports `rollback_last_write`; `preview: true` returns the proposed diff without writing. `smart_edit_batch` prepares up to ten distinct files before applying changes and also supports preview. If a later edit fails, it attempts to restore earlier ones only while their hashes match. This is not an atomic multi-file transaction: interruption, Docker failure or concurrent changes can leave changes requiring manual inspection.
- `diagnose_project` detects common project markers and performs bounded static syntax checks, prioritizing changed files; it uses an installed local TypeScript compiler when available. It compares diagnostics with the previous observation where the same checks were performed, without claiming an observed difference was caused by a change. It reports skipped checks and does not run tests, import project modules or run Django commands. Running a project-provided compiler executes code inside the sandbox.
- `verify_task` reports observed tool results, changed files and the freshness of diagnostics and test results. It runs no checks itself and does not declare the task complete.
- `security_scan` defaults to a bounded heuristic scan for several possible security issues. An optional `semgrep` engine uses the bundled rules and requires Semgrep installed in the project's `.venv`; it runs inside the network-isolated sandbox. It ignores Git ignore rules while excluding common dependency, build, configuration and session paths, so other Git-ignored files may be scanned. Results omit matched source and secret values, require manual review and cannot establish that the project is secure. The bundled rule set is intentionally small.

No new tools require the agent to write automated tests. File hashes and diagnostics are scoped to the current task; filesystem changes outside the included Shadow Git inventory cannot be reflected in its freshness checks.

After changing sandbox code, rebuild the image:

```sh
docker build -t diabolix-sandbox:local sandbox
```

Ordinary commands have no network access; dependency installation uses the restricted temporary network described above. Direct `npm install`, `npm i` and `pip install` commands in `run_command` are rejected before execution with a suggestion to use `install_dependencies`; this also covers common `python -m pip` forms. This convenience filter does not analyze arbitrary scripts or every possible shell expression. Synchronous Python and Node.js commands can use normal shell redirections such as `2>&1`, quoted arguments and heredocs. Background servers and daemons are prohibited by the instructions and checked by a command filter for common shell operators and server invocations. The filter cannot reliably identify every possible server or infinite program, especially in scripts or complex shell syntax; Docker isolation and command timeouts remain in effect.

## Local settings and Full Auto

Frontier is the single agent engine. Existing local settings from earlier releases are migrated without retaining their former execution-mode choice; task history remains readable.

During a coding task, **Start implementing** interrupts ongoing recognized exploration or a pending model request without cancelling the task and enables execution priority for that run. The agent continues using the observations already collected. Further recognized file exploration, web search and common shell-read commands require the model to state a concrete blocking unknown and obtain a one-call permit for exact arguments. Repeated identical investigations are blocked until the workspace changes. This is an execution policy, not proof that the model’s stated reason is valid: arbitrary shell commands and third-party MCP tools cannot be classified perfectly, and remote MCP servers may not honor cancellation. The priority is retained when the same interrupted task is resumed. The normal Stop button still cancels the whole task.

Settings are stored in `config.local.json`, which is excluded from Git. If you enable key persistence, the key is written to this file **without encryption**, with owner-only file permissions. The configured settings file is masked inside DiaboliX's containers, but copies of secrets and third-party host tools are not protected by this mask. The API does not return keys. To remove a saved key, disable the checkbox and save the settings.

Full Auto disables the user-configured step limit but retains an emergency limit of 500 steps per task and repeated-call protection. This mode can increase API costs. Click **Stop** to interrupt execution. Research has no separate fixed read-count limit: the Frontier agent and delegated workers may continue obtaining new observations, and the research guard warns or stops only after consecutive results yield no new information. New lines, changed file contents and new search observations reset that streak. Observation comparison is bounded and heuristic, not a semantic proof of novelty. The configured task step budget and Full Auto safety ceiling still apply; shell commands and actions with side effects retain their separate safeguards.

While a task runs, the same message box accepts clarifications. The in-flight tool is allowed to finish, later unstarted calls from that response are skipped, and queued clarification is sent on the next model request. The interface distinguishes queued, applied, unconfirmed and undelivered messages; applied does not mean the model obeyed them. User clarification does not automatically cancel a running side effect. Explicit test/browser prohibitions are handled by best-effort language and command recognition, not a security boundary.

The tool context retains full results from the last four model interactions with tools; older results are replaced with brief summaries. Unchanged repeated reads are suppressed while the original result remains in the context window; once it is compressed, the file can be read again. The stable system prompt does not contain the dynamic plan or project map. Actual server-side prompt caching depends on the provider and request parameters. Frontier uses a bounded task-ranked view of changed and relevant files, task-local errors, decisions, a diff and the observed Python interpreter path. The agent also receives a bounded read-only snapshot of the current Git branch and tracked changes when the workspace is a Git root; untracked files are omitted from that view and task changes come from Shadow Git. A bounded initial survey of symbol names, source terms and approximate imports can improve path ranking, but is historical and partial; aliases and dynamic imports are not resolved, and hints are not proof of current content. Architecture decisions are journaled as unverified model interpretations; older evidence remains available through `read_task_evidence`.

### Project navigation, memory, and strategy search

DiaboliX builds a bounded local navigation index in the background while a coding task runs. It retains paths, hashes, syntactic symbol names and approximate relative imports, not file bodies, in `.diabolix-sessions/project-index/`. Indexing reuses unchanged entries, honors project `.gitignore` rules using a private temporary Git repository, excludes common generated and secret-like paths and symlinks, and refreshes after tracked workspace changes. File filtering is heuristic and cannot identify every sensitive name. Other existing tools and Shadow Git may include files ignored by project `.gitignore`; index exclusions are not a workspace-wide confidentiality boundary. The index is partial, can lag the workspace, and is only a path-ranking hint. Up to 20 candidates are hash-checked against a particular Shadow Git snapshot, including paths beyond the first inventory page; this does not prove the workspace stayed unchanged afterward or establish symbol meaning or import resolution. If indexing or Git is unavailable the agent continues with existing navigation tools. Stop and **Start implementing** request cancellation of background indexing; an atomic metadata-file rename already in progress may finish. A bounded partial scan does not resume from a cursor, so very large projects may remain partially indexed until a later scan. No embedding service or source-code upload is used for indexing.

Project memory is a bounded projection of earlier intact, completed task journals from the same configured workspace and profile. It includes selected model decisions and verified file-write references, not old file bodies or raw tool output. Decisions remain unverified interpretations. A matching hash means only that one tracked text file matched at a particular Shadow Git snapshot; it is not proof that an earlier task or test is still valid. Relevant items can be requested with `project_memory`, and their compact source references can be inspected. Loading is bounded and may omit older tasks. The agent receives relevant projections as untrusted data, so they may be sent to the configured model provider; heuristics and configured-key redaction cannot guarantee removal of arbitrary secrets. Journal content and local index metadata remain sensitive.

In **Settings → Project memory**, inspect bounded entries for the saved workspace/profile and choose **Forget** or **Restore**. Forgetting excludes that entry from the historical project-memory projection for future tasks; it does not delete the source journal, remove information already sent to a provider, or suppress explicit continuation ancestry. Changes are unavailable while a task is active. The local exclusion file is stored in `.diabolix-sessions/`; a damaged exclusion file disables historical project-memory projection rather than revealing excluded entries. If that file is removed entirely, prior exclusions are lost and those historical entries can reappear. Exclusion updates are serialized within one server process; do not run multiple servers sharing the same session directory.

The optional **Strategy Search** setting is off by default. When enabled, the Frontier agent can explicitly compare substantially different approaches to a difficult decision. It runs no tools or speculative code and uses at most six additional logical model requests, a 60-second deadline, bounded input/output and the task's remaining step budget. Provider retry handling can make additional HTTP attempts within that deadline. The search checks the tracked Shadow Git tree before and after, is interrupted by Stop or **Start implementing**, and falls back to ordinary execution on error. Its plans and scores are model-generated advice, not proof of quality or execution. This is a bounded one-level comparison using the existing MCTS-inspired planner, not full Monte Carlo simulation. It is never a mandatory stage.

### Frontier delegation

The primary agent may call `delegate_tasks` for two or three substantial independent tasks with non-overlapping project paths. DiaboliX creates separate worktrees from its private Shadow Git checkpoint, runs bounded subagents concurrently in Docker and returns their proposed diffs. It never applies those proposals automatically: the primary agent must inspect the current files, integrate the changes and handle conflicts using normal editing tools. Subagents cannot use MCP, recursively delegate or install packages; excluded files, binary files and dependency directories are absent. Their model calls count toward the task step limit. Diff output is bounded and may be incomplete; `read_delegation` pages through the available proposal. `parallel_read` performs up to four independent read-only operations with separate journal references.

The harness reports observed checks and unconfirmed requirements at completion. An optional `request_review` invokes an independent reviewer and returns its feedback to the agent; the agent decides what to do next. A source citation alone does not establish that a requirement is met. The agent may run existing tests and browser scenarios when useful, unless the user explicitly forbids them; browser checks also require Computer Use. It is instructed not to create new automated tests unless requested.

## Checkpoints, telemetry, and long contexts

Task events are stored as local JSONL files in `.diabolix-sessions/` beside the config, with owner-only permissions. The directory is ignored by Git and masked inside the built-in containers when it is in the workspace. The journal contains task text and tool results, so it can contain project data; configured API and bot keys are redacted and screenshots omitted, but arbitrary secrets in project data cannot be reliably identified. History is viewable after a restart. A task without a terminal event is marked interrupted, not successful. The history shows up to 100 recent tasks.

An explicit **Continue** starts a new attempt with the original task and recorded tool statuses, rather than replaying an old model conversation or restoring a LangGraph checkpoint. It is restricted to the same coding workspace, confirmed read and file-write tools, and matching hashes for verified file changes; unconfirmed writes, in-flight calls, shell commands, and external tools require manual review instead. The new attempt has a new rollback baseline. This check does not prove that every other file or external state stayed unchanged.

Test, project-diagnostic and post-edit diagnostic observations compare a pinned sandbox image and selected manifest/lock files before and after execution, and recheck them when reporting freshness. This is explicitly partial: installed dependencies, environment variables, PATH, running processes, services and other files may change unnoticed. Unknown or changed selected environment state prevents a fresh claim. An open task-scoped process container is treated as potentially mutating until its cleanup is confirmed. Journal-only summaries retain the historical result but do not assert live environment freshness.

Tool events include structured status evidence separate from model summaries. A short window of statuses is included in subsequent prompts; it is not proof that the full task is complete. The agent and optional reviewer can use `read_task_evidence` to list recent actual tool results and retrieve a result by event ID after context compaction (long results are truncated).

### Shared task memory

Shared memory is a bounded, read-only projection of the existing `.diabolix-sessions` journal, not a separate model-controlled database. The harness records tool observations with source event IDs, model-proposed decisions and optional reviewer assessments in the task journal. Configured credentials are redacted from projected memory and retrieved journal evidence; arbitrary project secrets cannot be reliably detected. A journal write failure produces a warning; OS or power failure can still interrupt buffered filesystem writes. The agent receives a bounded task-relevant view; recent tool turns remain in its conversation when needed for the provider's tool-call protocol. Historical research, plans and older assessments remain available as non-authoritative context. `project_state` includes the worker view, and `GET /api/task-memory?id=<run-id>&role=worker` exposes a view to the local client. `read_task_evidence` can retrieve a source event from the current run or a recorded ancestor.

Requirements are derived by the harness from the original user task: `R1` represents the whole task and up to twelve additional entries quote explicit list items. The list can be incomplete; the full original task remains authoritative. The reviewer may assess a requirement and cite source IDs, but cannot create trusted facts or requirements. `supported_by_reviewer` means that at least one cited observation exists, succeeded and has current, tracked-file provenance; it is the reviewer's interpretation, **not proof that the observation logically establishes the requirement**. Missing, failed, truncated, unknown, fabricated or stale sources leave the requirement `unconfirmed`. Legacy reviewers can omit the per-requirement list; those requirements remain unconfirmed, even when the reviewer gives an overall approval. The console, task history and Telegram completion message distinguish unconfirmed requirements or sources requiring revalidation.

For a successful file read, the harness compares the actual displayed lines with the tracked file in the Shadow Git tree; verified writes are matched against the tree using SHA-256. A later change to the included tree makes those observations stale. This freshness check covers only tracked text files: ignored dependencies, binary files, external tools and live web data can have unknown freshness. A model-generated summary or plan is always labelled as an interpretation. On explicit continuation, source links are restricted to the current task's same-workspace, same-profile ancestry (up to eight prior runs); prior-run observations have unknown freshness until rechecked. Older task notes remain available as unverified legacy notes. The journal and memory are not a live model checkpoint.


A separate temporary Git repository is created outside the project for the current task. It stores the initial state and intermediate text-file changes without modifying the project's `.git`. After the task finishes, its changes can be rolled back to the initial state. The optional **Preview rollback** button lists bounded proposed file actions, path conflicts and scope limitations before the existing one-click rollback; it is advisory and the actual rollback rechecks current state. Rollback is sequential and an error can leave a partial result. Rollback is rejected if text files changed after the task finished; changes made manually *during* the task cannot be automatically distinguished from the agent's changes.

Binary files, symbolic links, `.env*`, `config.local.json`, and generated dependency and cache directories including `.git`, `node_modules`, `.venv`, `venv`, `__pycache__`, `dist`, `build`, `.next`, and `coverage` are excluded from snapshots and rollback. Installed dependencies are therefore not removed by task rollback. Temporary data contains copies of source code and is removed when the next task starts; it may remain in the system temporary directory after a crash. The current task's checkpoint and rollback do not persist across server restarts.

Changes are checked automatically: JavaScript with `node --check`, JSON by parsing, and TypeScript with local `tsc --noEmit` when both `tsconfig.json` and the compiler are available. Otherwise, the reason for skipping the check is reported. Events are delivered over SSE; token statistics depend on the provider including `usage` in its responses. The context-compaction threshold uses a UTF-8 size estimate and, when available, the provider’s last reported prompt token count; it does not guarantee that a request fits a particular model’s context window. A root-level `DIABOLIX.md` or `.diabolixrules` file is read at the start of a task, up to 4 KB.

When a model-provider API request fails, DiaboliX makes up to ten retries at 30-second intervals after the initial attempt. The console shows the retry count, and stopping a task interrupts both a request and the wait. An unsupported reviewer image is handled immediately by the existing text-only fallback.

After a file change, **Summary changes** opens a complete, color-coded diff against the start of the current task. New files appear as added lines. The view uses the same exclusions as the shadow checkpoint above and remains available after a page refresh while the task's checkpoint exists; it is replaced when a new task starts or the server restarts.

## Computer Use

When Computer Use is enabled and the user has not explicitly forbidden browser or automated checks, the agent can call `browser_test` when useful. It starts the supplied local application command and headless Chromium with Playwright in a separate short-lived container without networking, or attaches Chromium to an already running task-scoped process container using the same isolated network namespace. It allows only a local HTTP URL and up to 20 bounded steps, including same-origin navigation, visibility, text, value and URL checks. Unexpected main-document HTTP errors fail by default; an expected error status can be specified explicitly. It returns a screenshot, per-step results, browser errors and bounded HTTP diagnostics. The mounted project is writable, and the application command can change it. The browser container and any server it started are removed on completion, cancellation or timeout; an attached task process remains until stopped or the task ends. Rebuild the image after updating this component:

```sh
docker build -t diabolix-computer:local computer
```

This is a bounded browser scenario, not an assertion that the full application works. A syntax check or browser observation is not a substitute for a test suite. The agent may run existing automated tests when appropriate and respects explicit prohibitions; it is instructed not to create new tests unless requested.

Computer Use is an opt-in, experimental graphical desktop for the **agent**, separate from your host desktop. Build the desktop image once:

```sh
docker build -t diabolix-computer:local computer
```

In connection settings, enable **Computer Use** and select an OpenAI-compatible worker model that supports image input and tool calling. The worker discovers and invokes the `computer` tool through the built-in authenticated MCP server. When needed, the agent starts a dedicated Linux desktop containing Chromium and a terminal; the interface shows screenshots after actions. The agent can open HTTP(S) URLs or `about:blank`, take screenshots, click, double-click, move and drag the mouse, scroll, type, press supported keys, and wait. For navigation, DiaboliX waits for Chromium to report the active document URL and completed load before capturing the result; a timeout is reported as an error with a screenshot rather than a confirmed page load. The desktop lives for the current task and is removed on completion or stop. It has no host display, Docker socket, or host clipboard. Networking is off by default; enable **Allow internet for the desktop** in settings to browse websites. When enabled, the container uses Docker bridge networking without destination filtering and can also reach accessible local-network addresses. The separate web-search MCP tools keep their own network restrictions.

Chromium runs with its own sandbox disabled (`--no-sandbox`) inside the restricted Docker container. Browser sandboxing is disabled even when internet access is enabled. The selected project is mounted read-write: applications in the desktop can modify its files, including through the terminal. Screenshots can contain project data and are sent to the configured model provider; enable the feature only for data and providers you trust. The screenshot pane is an observation view, not an interactive remote desktop or a human takeover control. This is not a full Claude Desktop equivalent: it does not control your Mac, provide human takeover, or implement every native computer-use protocol. The worker model and provider must accept image input in OpenAI-compatible Chat Completions. If the image is unavailable, rebuild it with the command above.

File creation and edits are checked by comparing the resulting file hash with the intended contents. The sandbox also runs post-edit diagnostics: JavaScript and Python syntax checks, JSON validation, or TypeScript type checks when a local compiler and configuration are available. The agent may run existing tests when appropriate unless the user forbids them, and is instructed not to create new tests unless explicitly requested.

## Synthetic evaluation

`npm run eval` runs small synthetic JavaScript, TypeScript and Python coding tasks in temporary workspaces, with independent checks in Docker. Set `DIABOLIX_EVAL_ENDPOINT` and `DIABOLIX_EVAL_MODEL`; `DIABOLIX_EVAL_API_KEY` is optional. `DIABOLIX_EVAL_CASE` optionally selects one case, `DIABOLIX_EVAL_REPEATS` sets 1–10 attempts per case, and `DIABOLIX_EVAL_TIMEOUT_MS` sets the per-case timeout. Results and redacted event logs are saved under `.diabolix-eval-results/`, which is excluded from Git. Explicitly launching this evaluation runs its independent checks; the agent itself is not asked to write tests. These fixtures are smoke tests, not a SWE-bench score or a comprehensive quality benchmark.

Set `DIABOLIX_EVAL_MODEL_REVISION` to the provider-reported immutable model revision when known. Version 2 reports include fixture and partial source fingerprints, Docker image identity, machine and environment metadata, and per-attempt results. `node eval/compare.js <report-a.json> <report-b.json>` marks A/B comparisons inconclusive when recorded conditions are missing, differ, or attempts are incomplete; when comparable within recorded conditions it reports paired changes, p50/p95 duration, tokens and provider-reported cost by currency. Source fingerprints intentionally exclude local/secret-like paths and do not prove identical full runtime or dependencies; provider model identity is self-reported and repeated runs are still needed. Old reports remain readable but cannot establish comparability. Reports contain endpoint origin, model revision, host CPU/OS metadata, tasks, events and diffs; configured keys are redacted, but arbitrary secrets cannot be guaranteed redacted. Keep reports private.

## SWE-bench prediction export

`node eval/swebench.js manifest.json predictions.jsonl` can generate predictions for a locally prepared SWE-bench manifest. Set `DIABOLIX_EVAL_ENDPOINT` and `DIABOLIX_EVAL_MODEL`, and optionally `DIABOLIX_EVAL_API_KEY` and `DIABOLIX_EVAL_TIMEOUT_MS`. Each manifest entry must contain `instance_id`, an absolute local `repo_path`, `base_commit` (a commit hash present in that repository), and `problem_statement`. The adapter clones each repository to a temporary workspace at the requested commit, runs DiaboliX there and exports `instance_id`, `model_name_or_path` and `model_patch` in the official JSONL prediction format. It never checks out or edits the source repository. Output files must not already exist; a companion metadata file records whether each agent run finished or was interrupted.

This adapter does not download the Verified dataset, repositories or benchmark environments and does not score predictions. Supply matching local repository mirrors and dataset entries, then explicitly run the [official SWE-bench evaluation harness](https://www.swebench.com/SWE-bench/guides/evaluation/) against the generated file. The official harness executes benchmark tests in its own Docker environments. A prediction export alone is not a SWE-bench score.
